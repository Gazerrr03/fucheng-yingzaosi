# 技术选型：图形库怎么取舍

## 结论

**WebGL2 原生 API + 自写轻量渲染层，不引入任何渲染库。** 渲染层预留一个后端接口，以后需要时可以加 WebGPU 后端。
开发工具只用 Vite + TypeScript。它们只负责打包和类型检查，不进运行时。

## 候选方案

| 方案 | 是什么 | 优点 | 缺点 |
|---|---|---|---|
| A. three.js / Babylon.js | 完整的 3D 引擎 | 开箱即用，有 glTF 加载、后处理 | 你明确不要引擎；体积和抽象层多，风格化 shader 反而要跟引擎的默认管线较劲 |
| B. regl / twgl / OGL | WebGL 薄封装（几百行到几千行） | 省掉样板代码 | 多一个依赖，只省一点点；对这个项目收益不大 |
| **C. 原生 WebGL2** | 直接调浏览器 API | 零依赖；所有浏览器都支持；这个项目的需求它全部覆盖 | 样板代码要自己写，大约 1500～2500 行 |
| D. 原生 WebGPU | 新一代浏览器图形 API | 现代 API 设计；有计算着色器；CPU 开销低 | 老设备和部分 Linux、Android 浏览器还不稳定；调试工具不如 WebGL 成熟 |
| E. WebGPU + WebGL2 双后端 | 两套都写 | 新旧设备都兼顾 | shader 要写 WGSL 和 GLSL 两份，渲染代码也基本写两遍，工作量约 ×1.7 |

## 判断依据：这个项目到底要画什么

| 需求 | 需要的 GPU 能力 | WebGL2 够不够 |
|---|---|---|
| 大底图 + 六边形网格叠加、悬停高亮 | 一张贴图，加片元 shader 算六边形距离场 | 够 |
| 地图上的图标、选中发光 | 实例化绘制，加一点后处理 | 够 |
| 云雾过渡 | 几层半透明贴图做动画，2D 合成 | 够 |
| 3D 地块：几十个 glb，总共不到 15 万面 | 普通网格绘制 + 平光或卡通光照 | 够 |
| 移轴（tilt-shift）、轻微雾化 | 一次全屏模糊后处理 | 够 |
| 水面波纹 | 片元 shader | 够 |

WebGPU 真正领先的地方是**计算着色器**（大规模粒子、GPU 剔除、物理模拟）和**超大量 draw call 时的 CPU 开销**。这个项目两样都用不到：画面量很小，瓶颈在美术资产，不在渲染性能。所以选 WebGPU 拿不到实际好处，却要承担兼容性和调试的成本。

## 什么时候值得加 WebGPU 后端
- 地图上要放成千上万个动态元素，比如人流、船只动画。
- 要做 GPU 粒子云雾，而不是贴图云雾。
- 之后想做大范围的程序化地形。

为此，渲染层这样分层，后端可以替换：

```
game/            关卡逻辑、收集进度、状态机（不碰 GPU）
scene/           相机、六边形网格数学、地块场景装配
render/
  api.ts         抽象接口：createBuffer / createTexture / createPipeline / draw / renderPass
  webgl2/        v1 实现
  webgpu/        （预留）
ui/              HTML/CSS 浮窗、基因面板、云雾遮罩层（DOM + CSS 动画）
data/            三城关卡 JSON
```

## 自己要写的部分（大概工作量）

| 模块 | 说明 | 规模 |
|---|---|---|
| 数学 | vec3 / mat4 / 四元数；不想手写的话可以引入 gl-matrix（约 30 KB，只是数学库，不算引擎） | 约 300 行 |
| glTF 加载 | 只支持未压缩的 glb：网格、单张 baseColor 贴图、节点变换 | 约 300 行 |
| 六边形网格 | 坐标转换、拾取、邻居计算（参考 redblobgames 的六边形算法） | 约 200 行 |
| 相机 | 地图视角：平移和缩放，限定倾角；地块视角：环绕旋转 | 约 200 行 |
| 渲染管线 | 底图 pass、网格叠加、模型 pass、后处理 pass | 约 800 行 |
| UI 与状态 | DOM 浮窗、进度、存档（localStorage） | 约 600 行 |

## 浏览器目标
- 桌面端 Chrome、Edge、Safari、Firefox 的近两年版本。
- 移动端 v1 不做专门适配，只保证能打开、能点。
